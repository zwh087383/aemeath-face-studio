# 第二轮有界云端补测：实际结果与未通过项

2026-10-27。测试冻结源码为 `4713dd1`，与 [ROUND2.md](ROUND2.md) 的本地实现验收分开。结论是：提前请求、输入压缩、执行反馈和保护链路已在真实调用中运行，但动作仍晚，重复动作明显，没有达到自然连续阅读的目标。没有用预排动作掩盖失败。

## 实际测试了什么

四轮输入依次为：挥手并纠正饮料偏好、追问纠正后的偏好、在真实阅读中请求介绍发现并比较三种放松方式、出声中插话要求一句话建议。第一、二、四轮使用本机合成用户语音，第三轮改为文字输入以留足监听预算；Qwen 的回答、表情及动作均现场生成。第三轮不能计入“用户说完到首声”统计。没有把完整未来台词提前交给动作模型，没有手动发送身体动作指令。

只启动一项真实 WAI 阅读，读取 NASA 月球事实页面并产生笔记。使用隔离的合成用户状态和记忆；Neo4j、摄像头及自主定时器未启用。后台排期与恢复等待按 30 倍折算，活动最低 120 秒，实际模型请求、音频和动作保持原速。本批没有额外设置四组情绪初值；启动清单继承的 `four_explicit_math_fixtures` 标签不能作为实际执行四个情绪案例的证据。当前情绪从该隔离 WAI 数学状态读取。

云端走已存在的本机代理。启动时 GPU 利用率 63%，显存 6,755/12,227 MiB，未隔离其它机器负载，也未随机交错运行新旧版本。旧记录只作历史参考，不宣称严格 A/B 性能提升。

## 实际延迟

首声取浏览器 AudioContext 内属于本响应的首个有声采样点，不是服务端首包，也不是物理扬声器测量。身体起势取执行器开始帧；“可见变化”另记录了骨骼变化帧。

| 场景 | 用户说完→首声 | 语音请求→首声 | 身体起势晚于首声 | 实际结果 |
| --- | ---: | ---: | ---: | --- |
| 挥手并纠正饮料 | 2.309 s | 0.662 s | 未起势 | 纠正生效后旧上下文被撤回，声音与动作取消；不能算挥手同步通过 |
| 追问喜欢的饮料 | 2.767 s | 0.986 s | 2.414 s | 正确回答无糖乌龙茶，播完并写入历史；却又选了此前的挥手 |
| 阅读中要求长回答（文字） | 不适用 | 1.767 s | 未起势 | 实际已经出声，然后被下一条用户语音打断；收到指令不等于身体执行 |
| 插话后一句话建议 | 4.549 s | 1.796 s | 1.902 s | 播完并写入历史；仍出现不必要的挥手 |

两个实际起势样本的可见骨骼变化分别晚于首声 2.450 s、2.002 s。第一轮与第三轮没有动作起势，不把缺测记成零延迟。第一轮的有声回复虽使用了纠正后的词语，随后仍被纠正来源保护撤回；这说明保护成立，但用户体验尚需优化。

旧批次可用身体起势延迟约 2.28–3.56 s；本批两例为 1.90–2.41 s。场景、历史与运行条件不同，样本也少，不能据此写成稳定提速百分比。

## 动作的时间具体花在哪里

三个未被来源纠正取消的首次动作请求如下。这里统一以动作请求发出为起点，避免把本地准备和模型输出混在一起。

| 指标 | 饮料追问 | 长回答 | 插话后的短回答 |
| --- | ---: | ---: | ---: |
| 动作模型实际输入 tokens | 5,437 | 6,908 | 5,667 |
| 请求发出前本地准备/确认 | 47 ms | 63 ms | 109 ms |
| 动作请求比语音请求早 | 62 ms | 125 ms | 63 ms |
| 请求→首块工具参数 | 687 ms | 968 ms | 985 ms |
| 首块参数→首个完整工具参数 | 2,719 ms | 2,172 ms | 2,719 ms |
| 请求→完整身体工具参数 | 3,406 ms | 3,156 ms | 3,719 ms |
| 完整身体参数→后端发送 | 0 ms | 0 ms | 0 ms |
| 浏览器收到命令→身体起势 | 39.4 ms | 未起势 | 27.7 ms |

旧批次已记录的三次对应类别请求输入为 15,541、15,558、17,285 tokens。输入压缩确实落到了服务端用量上，但不能把这三个不同问题当作配对实验。

本批 23 次有完整终态计时的动作决策（含后台和续选）输入范围 4,985–7,113 tokens，中位 5,781；请求到首块参数中位 641 ms，到首个完整工具参数中位 2,531 ms，范围 1,422–5,203 ms。另一条因纠正撤回，仍保留账本及错误事件，未混进该分布。

这说明现在主要等待仍在工具参数陆续输出到完整指令之间。首块到达前也包含网络与云端调度，不能直接叫作 prefill。当前执行端等待完整合法工具参数才执行，没有为了提前起势猜测半截 JSON。进一步降低输入 tokens 可能有帮助，但不会自动消掉后面两三秒的输出等待。

字幕已不再被“整段播完”强制挡住：正常追问和插话后短答的第一条字幕决策，分别在实际播放结束前约 2.42 s、1.14 s 发出。但同一动作决策队列还会排队，观测到 1.38–2.83 s 的等待；再加工具生成，仍可能错过语音。取消整段门控有效，不等于端到端同步已经通过。

插话后首声较慢也有单独来源：该轮本地上下文准备 1.578 s，前三轮约 0.391/0.469/0.625 s；请求到实际首声又用了 1.796 s。没有证据把这两段都归给动作调度器。

## 完成回执通了，但自主续选还不好

后端接收并验证了 23 条实际执行结果，16 次触发模型再决策。共收到 22 条身体命令，只有 2 条写了持续目标，没有一条显式选择 `review=wait` 或 `on_failure`。当前缺省是 `on_finish`，所以成功完成后仍会再询问模型。这使重复的成功动作变成新一轮决策的诱因，重复失败保护无法解决它。

本批实际完成：挥手 5 次、好奇 8 次、短暂思考 1 次、解释 1 次；另有解释 5 次及招呼 3 次因错过语音锚过期。其余被撤回的执行结果按来源拒收，没有冒充完成。22 条命令不等于 22 次成功动作。

阅读活动的模型选择为 8 次好奇、1 次短暂思考，另一次保持；没有选择坐下、取书、读书等生活能力。八个生活动作仍在全部 83 项合法能力目录中，未被本地候选过滤器藏掉。动作模型确实拿到完成/失败反馈，但没有据此形成理想活动目标。

正常追问和插话后短答都再次选了挥手，尽管当前问题没有新挥手要求。这是实际观察到的旧意图延续问题；目前只能指出历史、原目标与当前请求边界需要加强，不能凭单批数据断言纯粹是模型能力或某一句提示词造成。

后台业务本身完成了开始→暂停→恢复→完成：约第 118.33 秒因交谈暂停，第 153.63 秒恢复，第 157.02 秒完成，产生真实笔记《月球事实阅读笔记：一颗豌豆与一枚五分镍币》。长回答引用了阅读材料中的发现。活动恢复和完成时动作额度已经用尽，对应新决策被明确跳过。因此业务生命周期通过，**恢复/完成阶段的模型动作与完整阅读表演未通过本批验收**。

后续改进应让模型明确表达“目标完成，保持现状，等新事件”，区分新请求与已满足的旧请求，并缩小第一份可执行指令；不能靠程序补上固定读书动作链。本报告没有擅自改默认策略后继续追加云端调用。

## 打断、表情与历史保护

长答实际开始出声后注入真实流式用户 PCM。开始送入该片段到浏览器本地暂挂音频约 **173.4 ms**，其中包括片段前导与分块发送；不是声学开口到物理停声的测试。本地有声检测触发后约 0.1 ms 进入暂停。又过约 **2.774 s**，云端断句确认插话，取消操作本身约 1.1 ms，丢弃约 **22.331 s** 旧待播音频，旧回复未恢复。

取消时没有正在执行的身体动作，因此这次证明出声中插话与待执行指令撤回，没有证明挥手运动中断。声音没有等动作工具回执。最后播放器正常 ended，队列清空、无音频错误；记录中存在最高 446.6 ms 的绘制帧间隔，不能宣称整段动画绝无卡顿。

持续脸与口型分离使用的是已通过本地回归的新版，原速录像保留实际显示；本批模型只选择了 warm、curious、smile 三种语义表情，不能冒充八种表情均已完成真实对话验收。新版/旧版的同条件表情组件对照仍可在免费页切换，组件样本不算云端自由对话。

最终历史：4 条用户输入，2 条完整确认助手回复，2 条取消投递，未把生成完但没播完的长答记作完整历史。待确认投递为 0，回复后效 5 项、输入维护 12 项全部完成，运行时排空成功。饮料纠正后检索正确，旧账本 SHA256 与测试前一致。
