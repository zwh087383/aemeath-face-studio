# 动作与语音同步：2026-10-24 实验复测

本轮修掉了本地丢动作和额外等待，但尚未做到模型指定动作与首声同时出现。现在语音立即播放，完整、合法的动作命令到达后，表情和身体使用同一个媒体位置接入。保留原身体幅度、近身肘部、利落挥手、起手与收势，不通过加速动作或推迟语音掩盖差距。

## 原来哪里出了问题

播放器的 buffering 既可能是第一次等待音频，也可能是已经播到一半、下一包还没到。旧工具适配器把两者都排在第0秒。greet-r2-B 已播到0.4秒时收到挥手，被调度器正确的迟到保护拒绝，最终手和脸都没动。现在按真实媒体游标排队，缺音时冻结，恢复后继续；全局迟到保护和轮次检查没有放松。

实验页以前给已到达的工具再加60ms等待。现在去掉这层等待，脸和身体在同一播放位置排队。其他页面默认保留既有60ms配置，仅共用中途缓冲修复；新同步策略首先在本实验页验证。

首声以前只在画面刷新时检查。招呼首包400ms，第390.08ms才有声音，只有约10ms的有声尾巴，渲染帧可能错过它。现在直接记录该采样在AudioContext中的调度时间，音源结束也保留标记。旧RAF字段仍作为诊断，原云端记录不回写。两种计时不能直接混合宣称性能提升。此时间不包含物理扬声器的声学测量；设备延迟另存，系统休眠等特殊情况不在本轮结论内。

设备预检改为最多等待2秒观察音频时钟真正前进，避免冷启动设备超过旧160ms检查窗口就误报失败。预检失败不会请求云模型。

两版都用新版首声计时，按原始事件间隔发送相同PCM和工具。每版每场景一次；不能据此宣称稳定分位数。

| 招呼1：请求至首声 | 2614ms | 2597ms |
| 招呼1：身体落后首声 | 579ms | 517ms |
| 招呼1：表情落后首声 | 489ms | 429ms |
| 招呼2：请求至首声 | 2087ms | 2089ms |

招呼1差距改善约60ms，符合取消本地等待的预期。首声的几毫秒至十几毫秒差异属于回放调度波动，没有添加语音等待。招呼2证实缺音后的命令可被正确执行，不能把旧版缺失动作算成0ms。

文件在 outputs/early-action-20261024，名称分别为 greet-r1-B / greet-r2-B 加 -sync-legacy-replay-client.json 和 -sync-immediate-replay-client.json。页面“新旧同步对比”按相同场景播放两遍，下一次点击反转先后顺序；两遍之间也保持互斥，避免插入另一轮。

## 新增一次真实 Qwen 回复

沿用原14响应预算、原提示、上下文和台词，只补此前在建连阶段失败的 compare-r2-B，没有重置账本。先前失败记录归档到 connection-failures。当前12/14，全部已报告用量，没有未知用量。未继续调用已出现4次只给工具不给语音的C组探针。

| 这一次的阶段 | 时间 |
| --- | ---: |
| 请求发出→服务端首有声包 | 500ms |
| 请求发出→浏览器首声调度 | 902ms |
| 点击→浏览器首声调度（含建连） | 1218ms |
| 请求发出→完整工具到客户端 | 1391ms |
| 请求发出→身体可见变化 | 1489ms |
| 请求发出→表情通道可见变化 | 1665ms |

模型返回 neutral / explain。身体比声音晚587ms，其中完整工具本身就比声音晚489ms，再经约98ms自然起手出现可见变化。脸部比首声晚764ms，是这次neutral指令对应的通道变化，不是“开心表情”。工具和音频在同一个response内完成，均早于工具回执；没有第二次response.create补语音。

这次比旧批首声更快，可能含云端/网络/连接条件差异，不能全部归功于本地同步修改。CPU动作驱动P95约1.2ms，渲染提交P95约10.1ms，帧间隔P95约13.4ms。渲染提交不是GPU完成时间。

## 打断与保护

使用招呼2原录音，身体可见变化200ms后本地打断。打断时正在播放，有2个音频源。取消调用返回0.6ms，之后音频源和队列都为0；约10.2ms关闭嘴部，814.1ms完成自然收势，后到的保存事件未使旧动作复活。此为真实PMX/保存云端音频的本地回放，不是本轮新增的云端取消或物理麦克风打断。

84项Node回归和13项Python回归通过，覆盖音频标记、欠载、暂停、旧轮次、去重、取消、工具验证、源站门控、原云端报告不可覆盖和新旧回放分开保存。9份已有脏文件SHA256不变，原动作profile/controller/rig、衣发绑定和数学情绪权威源未修改。
