# 人话技术报告

让读者不看代码，也能判断方案是否完整、为什么这样设计、还缺什么。保留实现深度，降低术语负担；不能把“讲人话”简化成只讲目标、比喻或模块名称。

## 先回答用户眼前的问题

- 先给结论及其成立条件，再展开原因。问题是“接入前是否必须整理全部资源”，先区分完整流程与全部资源覆盖，不能直接给一张庞大的工作清单。
- 沿用户正在讨论的场景解释；一般问题用一两个具体例子，整套方案才逐环节展开。篇幅由问题决定，不强制固定章节数或长篇模板。
- 先用已有资料和必要的窄范围核对确认现状；资料不足就指出未知，不为写一段说明擅自修改程序、调用收费模型或做生产实验。

## 每个重要判断都要能追问到底

对会影响结果的判断，覆盖下面内容；可以合并为段落或表格，不必每句话重复相同小标题。

| 要交代的事 | 必须具体到什么程度 |
| --- | --- |
| 谁判断 | 是哪个已有模型、哪个本地程序、数学计算，还是制作与验收人员；如果分工，说明先后和最终决定权 |
| 根据什么 | 看哪些实际输入、上下文、场景记录或测量；它们来自哪里、是否仍有效；不能只写“综合多方面因素” |
| 怎样作决定 | 列出会改变结果的检查顺序、比较条件、完成标准或分支；“智能选择”“按规则判断”不能代替这些内容 |
| 怎么执行 | 从当前情况开始，经过哪些实际步骤；下一步靠什么事实启动；使用现有资源还是必须补能力 |
| 不知道或做不到时 | 区分没结果、结果不可靠、结果过时、明确失败；说明暂停哪部分、什么还能继续、谁负责重试或恢复、何时结束等待 |
| 如何证明做对 | 由谁检查、观察什么结果、在什么范围算通过；区分单项检查、真实运行、设备实测和连续观感 |

- 判断来自模型时，说明复用当前回复、已有后台分析，还是拟新增调用；提供什么信息、期待怎样的有限输出，以及是否会让用户等待。模型说“有把握”不能充当正确率或事实证明。
- 判断来自规则时，说明规则检查的事实和成立条件。“任务已开始”要读执行记录，“东西已放好”要看实际位置与承接条件，不能只靠模型台词或计时结束。
- 状态由数学或业务系统维护时，说明模型是否提供上游输入，谁产生最终状态。表现模块不能另造一套互相冲突的状态。
- 结果冲突或晚到时，指出哪个来源有权决定该项事实、如何核对较新的记录，不能笼统写“优先级较高者胜出”。
- 给出等待或重试边界。没有测量依据时，可以提出有理由的试调范围，但必须标为待测；也可以明确需要先测什么再定值，不编造精确数字。

## 把过程讲成可以执行的动作

- 使用“当前情况 → 条件检查 → 实际变化 → 完成依据 → 失败处理”的顺序。
- 遇到“自然过渡、平滑恢复、无缝接入、稳定运行、完整支持”，接着解释实际如何做到。例如从现在的位置与速度收手、落脚后再转向，或旧请求取消后拒绝迟到结果。
- 对连续过程说明中途变化：请求撤销、输入更正、目标改变时怎么办；不能只讲正常开始和正常结束。
- “保持”与“停止”也要具体：停止的是新决策、当前运动、输出还是业务？未知时不能默认全系统冻结，也不能默认全部继续。
- 把模型判断、资源说明和实际执行能力分开。写了“可以中断”不等于已经有可靠退出过程；有文件不等于已接入；局部实验通过不等于完整流程通过。

## 写准备工作时，交代范围与顺序

- 区分“所有资源都整理完”和“拟开放使用的那一部分准备齐全”。按问题判断是否可以先做一个端到端小范围，再扩展覆盖；不能把局部可行性当成完整接入。
- 分清必须先有、能并行、可以后做；说明缺这项会卡在哪一步。对真正必须全量完成的迁移或一致性要求，不套用分批开放。
- 区分可自动提取的资料、需要人工或实模确认的含义，以及必须补写的执行能力；不给每个文件凭空要求一份重复长文。
- 说明验证结果的适用范围和失效条件。一个模型、姿态、场景或版本通过，不能默认覆盖其它组合。
- 如果提出“最小完整流程”，明确它完整到哪里、不含什么，以及未开放部分如何处理。

## 可读性与证据

- 主文用角色和实际行为称呼负责方，例如“播放器”“负责回复的模型”“当前任务记录”。字段名、类名、公式、源码位置放必要的查证链接或附注；用户明确要接口时再提供。
- 术语确实省事时，第一次用一句日常话解释。不要换一套自造缩写或生硬标签继续增加阅读负担。
- 具体例子要包括能做与不能做的区别。避免只举系统成功的例子，也不要用大量假想异常淹没主要流程。
- 清楚标出已查到的事实、由事实推断的可能性、准备采用的方案、尚未验证的部分。数据注明测量位置和条件，不能拿推算或历史样本冒充本次实测。
- 表格适合比较选择、责任和前置条件；有先后的过程用短步骤或连贯段落。不要为每个细节堆一张表，也不要用整屏代码作为非专业读者的主解释。
- 写完检查：是否仍有无法追问的“合适、兼容、可靠、智能”；是否每个关键判断都有证据和未知处理；是否区分建议与事实；是否保持用户限定范围。

需要校准“详细但易懂”的写法时，读 [具体写法示例](references/examples.md)。示例只是说明写作方法，不是某个项目的现状或固定技术方案。用户只要求解释时，直接回答；要求文档时编辑对应文档，不擅自实施其中的方案。
