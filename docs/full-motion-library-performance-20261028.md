# 完整动作库扩展：本地画面、资源准备与声音复测

本轮使用本机 RTX 5070 Ti Laptop GPU、Chrome 无窗口模式和实际 PMX。没有调用云端模型，也没有测量新的语音首声延迟。旧版取自固定提交 `5b1f583556610da09e63d0eaf872340277dfd462`，从独立只读目录加载；新版使用本轮工作区。其它用户服务保留，每轮记录 CPU、内存、渲染器与音频处理块。

## 最终同布景对照

最终测量在活动代理的重型回归退出后串行进行。两版使用完全相同的显式布景：人物在原点，桌子位于 `[0,0,4.3]`，其它道具不可见；画幅为 1440×1000，相同挥手和本地音频。每页先真实绘制 6 帧，再测 8 秒。顺序为新、旧、旧、新，CPU 忙碌率约 21%–24%。

| 顺序 | 每帧间隔中位 | P95 | 最长帧 | 动作/场景控制中位 | 音频回调间隙 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 新版 1 | 16.3 ms | 19.6 ms | 33.2 ms | 9.6 ms | 0 |
| 旧版 1 | 16.6 ms | 21.5 ms | 46.3 ms | 9.6 ms | 0 |
| 旧版 2 | 16.7 ms | 19.8 ms | 34.5 ms | 9.7 ms | 0 |
| 新版 2 | 16.4 ms | 20.6 ms | 29.5 ms | 9.4 ms | 0 |

这组小样本支持“扩库后正常挥手的持续播放成本接近旧版”，不支持把 0.2–0.4 毫秒的差异宣称成确定提速，也不证明所有动作都稳定 60 帧。四次挥手均完成，音频均有非静音数据。

该浏览器进程第一张页面准备到可测共 **24.01 秒**，首次真实绘制占 **9.12 秒**；之后三张页面为 **5.25、5.75、5.12 秒**，首次绘制约 59–71 毫秒。缓存状态不同，不能用第一张新版与后续旧版的初始化时间直接比较。冷启动和持续播放分开记录，新版也没有一次加载全部 319 段。

最终同布景测量还包含以下两项：

| 场景 | 每帧间隔中位 / P95 | 最长帧 | 音频回调间隙 | 实际结果 |
| --- | ---: | ---: | ---: | --- |
| 挥手期间准备原生思索，观察 10 秒 | 19.0 / 33.6 ms | 182.9 ms | 0 | 挥手完成，资源已读好；10 秒窗口内几何准备尚未让动作起势 |
| 故意令原生资源返回 HTTP 503 | 16.9 / 20.3 ms | 24.7 ms | 0 | 挥手完成，只拒绝原生动作，声音继续 |

原生动作的源读取完成不等于场景几何检查完成，因此另外增加 35 秒连续窗口测量完整准备和开始，结果在下文单列，不能把上述 10 秒观察写成“原生动作已经完成”。

### 原生思索的 35 秒完整窗口

此轮 CPU 忙碌率为 23.2%，声音从测量开始持续独立播放。使用真实墙钟记录，避免把浏览器长帧时截断的模拟时间当作真实等待：

| 事件 | 从音频测量开始算起 |
| --- | ---: |
| 挥手开始 | 0.038 秒 |
| 原生思索排入队列 | 0.316 秒 |
| 挥手完成 | 3.526 秒 |
| 思索获准执行 | 12.297 秒 |
| 思索开始表现 | 12.391 秒 |
| 思索完整结束 | 18.742 秒 |

原生资源读取约 **255 毫秒**；排队到获准却约 **11.98 秒**，包含等待前一个身体动作结束以及实际场景几何检查。挥手完成后到思索获准仍有约 **8.77 秒**。这清楚说明“文件已经读好”不足以让该行为立即接上，当前准备成本主要留在后续流程，不能归因于下载慢。

35 秒内每帧间隔中位 **15.3 毫秒**，P95 **30.9 毫秒**，最长 **134.7 毫秒**；音频监测 **0 次间隙**，有非静音样本。两项行为都有完整完成回执。这证明声音独立继续和资源可以完成接入，但也暴露出动作接续等待仍长；后续优化应针对可复用的几何检查及提前准备，同时保持临执行时现场有效性校验。

## 较早批次保留的观察

第一次交错对照时，主机还有其它任务，测量期间 CPU 忙碌率约 73%–83%。当时使用各自产品默认布景，新版有拉出的椅子及不同人物初始位置；因此它不是严格同场景对照，最终结论以上面的显式同布景批次为准。没有停止用户的其它程序。

| 实测顺序 | 每帧总间隔中位 | P95 | 动作/场景控制中位 | 音频回调间隙 |
| --- | ---: | ---: | ---: | ---: |
| 新版，第 1 次 | 46.4 ms | 60.6 ms | 28.4 ms | 0 |
| 旧版，第 1 次 | 42.2 ms | 52.9 ms | 26.5 ms | 0 |
| 旧版，第 2 次 | 45.5 ms | 53.8 ms | 28.5 ms | 0 |
| 新版，第 2 次 | 41.7 ms | 55.0 ms | 24.5 ms | 0 |

这组结果只保留为当时各自布景下的性能诊断。它不是 60 帧验收：当时约为每秒 22–24 帧，也不能从差异断言扩库提速。

第一次完整初始化，新旧版本都约 61 秒，其中首次真实绘制各约 23 秒；之后页面约 13–14 秒就绪。初次 shader/蒙皮绘制成本单独记录，没有混进常态帧统计。新库只按选中行为加载原生组，没有在启动时加载全部 319 段。

## 边播放边加载，以及加载失败

同一批高负载下，新版播放中准备原生思索资源：帧间隔中位 50.4 ms、P95 79.8 ms、最大 327.2 ms，音频回调间隙为 0。故意令原生资源返回 HTTP 503 时，对应动作被拒绝，既有挥手完成；帧间隔中位 35.0 ms、最大 104.8 ms，**音频监测记录过 1 次回调间隙**。原始失败观察保留，不能写成“所有批次均零停顿”。

为核实这一点，2026-10-28 又做三项独立复测，记录每个音频处理块的真实长度与帧位置。此时 CPU 忙碌率约 20%–27%，与前批负载不同：

| 场景 | 帧间隔中位 / P95 | 最长单帧 | 音频回调间隙 | 实际结果 |
| --- | ---: | ---: | ---: | --- |
| 正常挥手 | 10.6 / 13.8 ms | 28.9 ms | 0 | 挥手完成，语音持续 |
| 挥手期间加载原生思索 | 12.7 / 22.5 ms | 214.2 ms | 0 | 挥手完成，思索资源通过并开始执行 |
| 原生资源故意返回 503 | 10.8 / 16.7 ms | 42.4 ms | 0 | 挥手完成，只拒绝思索资源，语音持续 |

这次原生动作在排队约 9.74 秒后获准、约 9.81 秒后开始；准备尚有可优化空间，不能把它说成即时加载。声音从测量开始即独立播放，没有等待这一准备。首次加载造成的画面尖峰也仍然存在。此轮测试的目标是验证等待关系、隔离故障和记录成本，不将正常中位数掩盖成“没有卡帧”。

音频监测采用已有 14.935 秒 WAV、浏览器 AudioContext 和 AudioWorklet。复测均检测到非静音样本，处理块为 128 帧、采样率 48 kHz，未发现处理帧号跳跃。它证明的是本地预缓冲声音在这些浏览器测试中的连续性；没有证明真实网络音频、麦克风、扬声器听感，亦不能排除其它负载下的系统调度停顿。

## 后续补齐的路线与落座成本

独立审查补上了行走路线检查：按真实桌腿、桌面、椅面、椅背、箱和平台位置，用 PMX 骨骼计算检查源路线及入口。空场景没有障碍时直接返回。准备和正式开始都要核对实际现场，因此不能声称这项成本只有一次或为零。

最终在同一显式桌面场景做两项真实浏览器检查，CPU 忙碌率约 21%–22%，持续播放已有声音：

| 选择 | 实际结果 | 准备调用 | 每帧中位 / P95 | 最长帧 | 音频间隙 |
| --- | --- | ---: | ---: | ---: | ---: |
| 向左走，路线避开桌子 | 挥手后正常接入并完成 | 120.8 ms | 15.6 / 21.0 ms | **260.3 ms** | 0 |
| 向前走，路线穿过桌子 | `activity_route_blocked_by_table`，没有起步 | 53.3 ms | 17.2 / 21.0 ms | 72.2 ms | 0 |

这些检查没有卡住声音，但向左走的进入帧有明显耗时尖峰，包含准备和开始时的现场复核，不能称为全程无卡帧。后续若优化，应将重计算分片或复用仍与现场一致的检查结果，不能删除真实障碍检查换取好看的帧耗时。本轮保留安全拒绝和这个实际成本。

Weak_Sit 的较早真实椅前布景复测中，资源和实模准备耗时约 5.6–7.0 秒；最后一次同时有其它 PMX 回归的复测为 **10.84–16.98 秒**。Sit01 为 **5.65–7.37 秒**。不同负载不能直接比较，但都说明动作准备还不是即时可播。

收到打断后，旧命令立即撤销；**身体仍按声明的策略走完必要源阶段**。Weak_Sit 在源动作 2、8.5、10.8 秒打断，身体还需约 **10.72、4.22、1.92 秒**才完全结束。Sit01 在 1.5、5、9.5 秒打断，身体还需约 **5.9、6.4、1.9 秒**。这一项不能称为即时停身。它与音频立即停止、待执行旧命令失效是不同指标，后续若要更快退到倾听姿势，需要给连续源片段另做并验收可用出口。

## 本地命令解析

扩库同时暴露了后端每次命令都深拷贝大目录的问题。移除内部重复拷贝、复用合法版本后的默认目录校验中位耗时从 165.504 ms 降到 0.562 ms。公开读取仍返回隔离副本，非法或删除的目录不会退回旧缓存。具体样本、边界与旧可选旁路容量兼容见 [本地协议优化记录](library-expansion-protocol-local-optimization-20261027.md)。这不是云端响应时间的提升。
